## Tech stack

Next.js (App Router) with React and TypeScript, Tailwind CSS, Next.js Route Handlers for the API, PostgreSQL, Prisma 7 with the `pg` driver adapter, Zod for input validation. One Next.js app, no separate backend.

## Local setup

Needs Node 20+ and a PostgreSQL database.

```bash
npm install
cp .env.example .env        # set DATABASE_URL
npx prisma migrate deploy   # builds the schema on an empty database
npm run db:seed             # 38 visible requests + 2 removed ones
npm run dev                 # http://localhost:3000
```

`npm install` also runs `prisma generate`. Run the tests against a running app with `npm test` (set `BASE_URL` if it is not on port 3000). The seed script wipes the request and note tables first, so only run it on a database you are happy to reset.

## Architecture

```
src/app/api/requests/...   Route Handlers (list, create, get, patch, delete, notes, transition, summary)
src/lib/request-rules.ts   All business rules and the transition table
src/lib/validation.ts      Zod schemas for every input
src/lib/errors.ts          One wrapper that turns any failure into the JSON error shape
src/lib/requests.ts        Row to JSON mapping and the "find a live request" lookup
src/components/requests/   List, form, detail view, status badge
prisma/                    schema, hand-written migration SQL, seed script
tests/api.test.ts          Black-box API tests of the business rules
```

The UI reads the same `TRANSITIONS`, `isLocked` and `canRemove` from `request-rules.ts` that the server enforces, so the buttons offered and the rules applied cannot drift apart. The UI is only a convenience: every rule is enforced by the API.

## Database design

- `ReturnRequest`: customer name, email and phone, order number, item SKU and name, quantity, reason, status, resolution, refund amount, timestamps and `removedAt` for soft deletion.
- `Note`: body and timestamp, foreign key to the request.
- **Reference** (`RET-2026-000001`) is generated by a Postgres sequence in the column default, so concurrent inserts cannot collide and the client cannot supply one.
- **Rule 3** is a partial unique index on `(orderNumber, itemSku)` that applies while status is not Rejected or Completed and the request is not removed. The database refuses the duplicate, even under concurrent requests (tested with five parallel creates: one 201, four 409).
- **Rule 2** is backed by CHECK constraints: a refund amount exists exactly when the resolution is Refund and is above zero, and Approved or Completed always has a resolution.
- **Notes** are immutable at the database level too: a trigger rejects UPDATE and DELETE.
- Search, filters, sorting and paging are all Prisma queries on the server, with indexes on status, reason and created date. Search uses case-insensitive `contains` on reference, order number, customer name and email. That is fine at this size; a trigram index would be the next step for large tables.

## API

| Method and path | Purpose | Success |
| --- | --- | --- |
| `GET /api/requests` | `search`, `status`, `reason`, `sort`, `order`, `page`, `pageSize` | 200 |
| `POST /api/requests` | Create | 201 |
| `GET /api/requests/:id` | Request with notes, oldest first | 200 |
| `PATCH /api/requests/:id` | Edit customer, item, quantity, reason | 200 |
| `DELETE /api/requests/:id` | Soft delete | 204 |
| `POST /api/requests/:id/notes` | Add a note | 201 |
| `POST /api/requests/:id/transition` | `{ status, resolution?, refundAmount? }` | 200 |

Errors always look like `{ "error": { "code": "...", "message": "...", "details": {...} } }`.

| Status | Codes |
| --- | --- |
| 400 | `VALIDATION_ERROR`, `INVALID_JSON` |
| 404 | `REQUEST_NOT_FOUND` (also for removed requests), `ROUTE_NOT_FOUND` |
| 409 | `INVALID_STATUS_TRANSITION`, `DUPLICATE_LIVE_REQUEST`, `REQUEST_LOCKED`, `REMOVAL_NOT_ALLOWED`, `REQUEST_CHANGED` |
| 422 | `INVALID_RESOLUTION`, `INVALID_REFUND_AMOUNT` |

## Business rules

1. **Status flow:** `TRANSITIONS` table in `request-rules.ts`, checked in the transition route.
2. **Approval needs a resolution:** `resolutionFor` in the same file, plus the CHECK constraints.
3. **One live request per item:** partial unique index. The API maps the violation to 409.
4. **Locked once decided:** `checkEditable` in the PATCH route.
5. **Removal:** `checkRemovable`, then `removedAt` is set. Every read path ignores removed rows.

Updates match on the status that was just checked, so a request that changes between the check and the write gets a 409 `REQUEST_CHANGED` instead of a silent overwrite.

## Design decisions and assumptions

- **No separate Customer, Order or OrderItem tables.** The brief has no order catalogue, so there is nothing to join to. Customer, order and item are stored on the request as the agent entered them. The cost is repeated customer data. A real store would reference its own order system.
- **Duplicate key is order number plus item SKU.** Order numbers and SKUs are trimmed and upper-cased on the way in so case changes cannot dodge the rule. Removing a request frees the item for a new one.
- **Locked means customer, item, quantity and reason.** Once decided, all of the request's details are locked.
- **Resolution and refund are only set through the transition call** that approves the request.
- **Removed requests return 404**, the same as ones that never existed.
- **Status codes:** state conflicts are 409, bad resolution or refund data is 422, malformed input is 400.
- **Refund currency** is shown as INR, matching the product context.
- **History is notes only.** Status changes are not logged.
- No authentication, since the brief does not ask for it.

## Verification and known limitations

Checked against the Supabase PostgreSQL database: all 15 API tests pass against the dev server and the production build, the migration reports no pending changes, the seed gives 38 visible requests across every status and reason, `tsc`, `eslint` and `next build` are clean.

Not verified or not done:

- Not deployed yet (see top).
- An unsupported HTTP method on an existing route returns Next's empty 405, not the JSON error shape.
- Search is a plain `contains` scan, not indexed.
- The tests need a running app and database; they are not wired into CI.
